# AgendaFotografo.WebApi

API única do sistema (assinante e administração). Namespace raiz: `AgendaFotografo.WebApi`. Portas: http 5289 / https 7118.
**Estrutura espelhada no Fartec.Portal** (referência obrigatória; ver a regra de ouro no `CLAUDE.md` da raiz): na dúvida, abra o arquivo
equivalente no Portal e copie o desenho.

## Controllers, rotas e nomes (regra do colaborador)
- Todos herdam `AgendaFotografoController` (`[Route("api/[controller]/[action]")]`, equivalente ao `PortalController`). Não existe `api/Admin`.
- Cada controller declara `[Authorize(Roles = ...)]` na classe (regra de ouro do Portal: controller sem role fica aberto). Exceção: `[AllowAnonymous]` explícito na action (Login, link público).
- **Os controllers seguem as tabelas e entidades**: tabela em MAIÚSCULAS no plural -> entidade no singular (PascalCase) -> `<Entidade>Controller` -> rota `api/<Entidade>/<Action>`. Exemplos do Portal: `CLIENTES` -> `Cliente` -> `ClienteController` -> `api/Cliente/*`; `MERECIMENTOS` -> `Merecimento` -> `api/Merecimento/*`; `CAMPANHAS` -> `Campanha` -> `api/Campanha/*`; `INSCRICOESCANCELADAS` -> `InscricaoCancelada` -> `api/InscricaoCancelada/*`. Tabelas filhas (ex.: `CAMPANHAITENS`) não têm controller próprio: viram actions do pai (`Campanha/Itens`). Controllers sem tabela (`Auth`, `Dashboard`, `Relatorio`) são nomeados pelo assunto.
- Nomes de actions (padrão do Portal; `id` na **query**, nunca no caminho):
  - `GET Listar` (paginada: `page`, `pageSize` padrão 25 máx. 100, `busca`, filtros; retorna `PaginatedResponse<XListItem>`);
  - `GET Obter?id=` (404 texto "<Entidade> não encontrado(a)");
  - `POST Criar` e `PUT Atualizar` (body `XModel`; 200 com o `XModel` salvo; `Atualizar` com `Id` vazio = 400, inexistente = 404);
  - `DELETE Excluir?id=` (200 `ApiResponse { Success, Message }`) quando a entidade pode ser excluída; senão `POST Inativar?id=` / `POST Ativar?id=` (flag `*_ATIVO`);
  - `GET Opcoes` (combo `[{Id, Nome}]`, `OpcaoModel`).
- Estrutura de pastas: `Models/<Area>/XModel.cs` + `XListItem.cs`, `Validators/<Entidade>/XValidator.cs`, `Controllers/XController.cs`.
- Construtor primário com campos `private readonly _repX = repX;`; toda action em `try/catch` com `BadRequest(ErrorHelper.Seguro(ex, _logger))`; regra violada = `throw new Exception("mensagem pt-BR")`; validação com `ValidationHelper.ValidateModel(model, new XValidator())`; sempre `CancellationToken`; leituras com `SelectContext().AsNoTracking()`; edição por entidade rastreada + `IUnitOfWork.SaveChangesAsync` quando houver colunas alimentadas por outros fluxos (ver Infra.Data). Mapeamento DTO/entidade manual ou Mapster.
- Transações: `IUnitOfWork.BeginTransactionAsync` antes do `try`, métodos `*TransactionAsync`, `SaveChangesAsync` + `CommitAsync`, `RollbackAsync` no `catch`.
- Dados do tenant: ver "Multi-tenancy" abaixo. Perfil Assinante usa `ErrorHelper.Seguro(ex, _logger)` quando for preciso esconder detalhes internos (usuário externo).

Regra de plural: nome da entidade em maiúsculas, plural na palavra que o Portal pluraliza (`Campanha`+`Itens` -> `CAMPANHAITENS`, `InscricaoCancelada` -> `INSCRICOESCANCELADAS`), sem separador. Toda tabela de negócio leva `<PREFIXO>_ASSINANTE_ID` (FK `Restrict` para `ASSINANTES`). O Portal usa `_` em três tabelas do Chamado (`CHAMADO_RESPOSTAS`); é exceção, não seguir.

## Autenticação (idêntica ao Portal)
- JWT Bearer (`Setup.AddCustomAuthentication`). `Jwt:Key` no appsettings (mín. 32 caracteres; `Setup.ObterJwtKey`; sobrescrita por User Secrets / `Jwt__Key`), `Jwt:ExpiraEmHoras` (padrão do código 8). Token gerado no `AuthController` com `JwtSecurityTokenHandler`, claims `NameIdentifier`, `Name`, `Email`, `Role`. **Sem claim de assinante.**
- **Revalidação a cada requisição** (`OnTokenValidated` + `SessaoUsuarioCache`, `IMemoryCache`, 30 s por usuário): usuário inexistente, `Ativo = false`, role diferente da do token, ou Assinante sem vínculo / com `ASS_ATIVO = false` = 401.
- Identity: `AddIdentity<Usuario, IdentityRole>`; única regra de senha: mínimo 8 (`RequiredUniqueChars = 1`); e-mail único. Bloqueio por tentativas: 5 senhas erradas = 15 min (`Lockout` no `AddCustomIdentity`; `AllowedForNewUsers = true`; o Seed garante `LockoutEnabled = true`).
- `POST api/Auth/Login` (anônimo): body `LoginModel { Email, Password }`; resposta `LoginResponse { Token, ExpiraEm, Id, FullName, Email, Role, ExigirTrocaSenha, AssinanteNome }`. `AssinanteNome` só para o perfil Assinante; **`AssinanteId` nunca sai**. O `Login` checa `IsLockedOutAsync` ANTES da senha; senha errada chama `AccessFailedAsync` (a 5ª já responde "Usuário bloqueado temporariamente"); senha certa chama `ResetAccessFailedCountAsync`. Erros: 400 texto ("E-mail ou senha inválidos", "Usuário inativo. Procure o administrador do sistema", "Usuário bloqueado temporariamente", "Acesso indisponível. Procure o administrador do sistema." para Assinante sem vínculo ou com assinante inativo).
- `POST api/Auth/AlterarSenha` (`[Authorize]`, qualquer perfil): body `AlterarSenhaModel { SenhaAtual, NovaSenha }`; 200 `ApiResponse`; 400 texto. Zera `ExigirTrocaSenha`. Não existe `Auth/Me`: o SPA usa os dados do login (e o 401 da revalidação).
- `ICurrentUser`: `UserIdentity` (`Id`, `Role`), `IsAdmin`, `IsAssinante`.

## Multi-tenancy (`AssinanteEscopo`)
Equivalente ao `ClienteEscopo` do Portal. `await _assinanteEscopo.ObterAssinanteIdAsync(cancellationToken)` lê `Usuario.AssinanteId` do banco a cada requisição. Perfil errado ou sem vínculo lança `AssinanteSemVinculoException`: o controller captura **antes** do `catch (Exception)` genérico e devolve `StatusCode(403, AssinanteEscopo.MensagemSemVinculo)`. Nunca usar id de assinante vindo de claim, body ou query; sobrescrever no model. Admin não tem tenant: nos endpoints do Admin o assinante é sempre um id explícito e validado.
Quem altera `ASS_ATIVO` (`AssinanteController`) ou o perfil/estado de um usuário chama `SessaoUsuarioCache.Invalidar(usuarioId)`.
Ao criar um `Usuario`, definir `CreatedAt = DateTime.Now` (como no Seed; o interceptor só audita `BaseEntity`).

## Setup, Program e Seed (idênticos ao Portal)
- `Setup.cs`: `MontarConnectionString` (único ponto; usa `MySqlConnectionStringBuilder`; `Db:Password` sobrescreve a senha), `ObterJwtKey`, `AddCustomDbContext` (`ServerVersion.AutoDetect`, interceptor), `AddCustomIdentity`, `AddCustomAuthentication`, `RegisterCustomServices`, `RegisterCustomSeedAsync`, `MigrationManager`.
- `Program.cs`: JSON `PropertyNamingPolicy = null`, Swagger só em Development, CORS por `Cors:Origins` (sem lista: aberto só em Development, outros ambientes nenhuma origem + `Warning`), pt-BR, log de servidor/banco/ambiente ao subir (nunca a senha), arquivos estáticos + fallback `index.html` (SPA publicada em `wwwroot`, rotas fora de `/api`), termina com `MigrateDatabaseAsync` e o Seed. Iniciar a API acessa o banco.
- `Seed.cs` (scoped, idempotente; recebe `EfDbContext` e `TipoEventoPadrao`): cria as roles de `RoleNames.All` (`Admin`, `Assinante`) e o admin `admin@agendafotografo.com.br` (com `LockoutEnabled = true`) com a senha de `Seed:AdminPassword` ou, se vazio, a constante `Seed.SenhaPadraoAdmin` (senha padrão no código, versionada no git por decisão do colaborador). Fora do Development o admin nasce com `ExigirTrocaSenha = true`. Admin existente nunca é alterado, exceto por habilitar o `LockoutEnabled` se estiver desligado. Depois, SEMPRE, dá os 7 tipos de evento padrão a cada assinante que não tem nenhum `TipoEvento` (ativo ou não), num único `SaveChanges`, e loga a quantidade.
- Serviços: `IEmailService`/`EmailService` (MailKit, singleton; `MailSettings` vazio por enquanto, usado no e-mail diário futuro), `AddMemoryCache`, `SessaoUsuarioCache`.
- Helpers: `ErrorHelper` (`GetException`, `Seguro`), `ValidationHelper`. Models comuns: `ApiResponse`, `PaginatedResponse<T>`, `LoginModel`/`LoginResponse`, `AlterarSenhaModel`.

## AssinanteController (plano 01; só Admin; `api/Assinante/*`)
Padrão do `ClienteController` + `UsuarioController` do Portal. `UserManager`, `IBaseRepository<Assinante>` e `IUnitOfWork` usam o MESMO `EfDbContext` scoped, então a transação do `IUnitOfWork` cobre assinante, usuário e role. Sem Delete e sem `Opcoes`. `id` sempre na query.
- `GET Listar?page=1&pageSize=25&busca=&ativo=true` (`ativo`: `true` padrão | `false` | `todos`; outro valor = 400 "Filtro de status inválido"; `pageSize` máx. 100). Busca no nome e no e-mail; no CPF/CNPJ só quando o termo, sem pontuação, tem apenas dígitos. Ordena por `ASS_NOME`, `Id`. Left join com o usuário de login (`ExigirTrocaSenha`, `LastLogin`). Retorna `PaginatedResponse<AssinanteListItem>`.
- `GET Obter?id=` -> `AssinanteModel` | 404 "Assinante não encontrado".
- `POST Criar` (body `AssinanteModel`): normaliza (trim, e-mail minúsculo, CPF/CNPJ e telefone só dígitos, vazio = nulo), valida, checa e-mail (qualquer usuário, inclusive o admin: "Já existe um usuário com este e-mail.") e CPF/CNPJ ("Já existe um assinante com este CPF/CNPJ."), cria `Assinante` + `Usuario` (role `Assinante`, `UserName = Email`, `FullName = ASS_NOME`, `ExigirTrocaSenha = true`, `LockoutEnabled = true`) com `SenhaTemporaria.Gerar()`, chama `IAssinanteInicializacao.PrepararNovoAssinanteAsync` (dentro da transação; hoje cria os 7 tipos de evento padrão via `TipoEventoPadrao`) e devolve `AssinanteSenhaTemporariaResponse` com `Cache-Control: no-store`.
- `PUT Atualizar`: só nome, CPF/CNPJ, e-mail e telefone (ignora `ASS_ATIVO`). Trocar o e-mail troca `Email`, `UserName` e `Normalized*` do usuário (manual, como no Portal; `SetEmailAsync` zeraria `EmailConfirmed`); trocar o nome atualiza `FullName`. Nunca toca senha, `ExigirTrocaSenha`, `Ativo`, `LastLogin`, `CreatedAt`.
- `POST Inativar?id=` / `POST Ativar?id=`: idempotentes; gravam `ASS_ATIVO`, fazem commit e SÓ DEPOIS chamam `SessaoUsuarioCache.Invalidar` para cada usuário do assinante. Devolvem `AssinanteModel`.
- `POST RedefinirAcesso?id=`: nova senha temporária (`GeneratePasswordResetTokenAsync` + `ResetPasswordAsync`), `ExigirTrocaSenha = true`, zera falhas e lockout (`ResetAccessFailedCountAsync` + `SetLockoutEndDateAsync(null)`), funciona com o assinante bloqueado, invalida o cache e devolve `AssinanteSenhaTemporariaResponse` com `no-store`. Não derruba a sessão aberta (o JWT não confere o SecurityStamp): para derrubar, usa-se o Bloquear. Sem usuário vinculado = 400 "Assinante sem usuário de acesso.".
- Log por `ILogger` com `AtorId` e `AssinanteId`/`AlvoId`; a senha temporária nunca é logada nem guardada.
- Serviços: `Services/Security/SenhaTemporaria` (cópia do Portal; 12 caracteres, sem ambíguos) e `Services/Assinantes/IAssinanteInicializacao` (scoped; contrato: roda dentro da transação do Criar, só grava com `*TransactionAsync`, nunca chama `SaveChanges`/`Commit`).
- Models em `Models/Assinantes/` (`AssinanteModel`, `AssinanteListItem`, `AssinanteSenhaTemporariaResponse`); validator em `Validators/Assinante/AssinanteValidator`.

## TipoEventoController (plano 02, etapa 2; só Assinante; `api/TipoEvento/*`)
Primeiro cadastro do tenant; é o modelo para `Membro` e `Organizador`. `[Authorize(Roles = RoleNames.Assinante)]`; toda action obtém `assinanteId` de `AssinanteEscopo`, filtra por ele e carrega por `Id` **e** assinante (outro assinante = 404). `catch (AssinanteSemVinculoException)` -> 403 antes do `catch (Exception)` -> `BadRequest(ErrorHelper.Seguro(ex, _logger))`. Sem Excluir: `POST Inativar?id=` / `POST Ativar?id=` (idempotentes, 200 com o model). `TPE_ATIVO` do body é ignorado (Criar nasce ativo; Atualizar mexe só no nome). Nome com `Trim`, obrigatório, até 60, único por assinante sem diferenciar maiúsculas e contando inativos (400 "Já existe um tipo de evento com este nome."). Atualizar: entidade rastreada + `SaveChangesAsync`. `Listar`: `page`, `pageSize` (máx. 100), `busca` (nome), `ativo` (`true` padrão | `false` | `todos`; outro = 400 "Filtro de status inválido"), ordenado por `TPE_NOME`, `Id`. `Opcoes?somenteAtivos=true&incluirId=` -> `[{Id, Nome}]` (`OpcaoModel`).
- `Services/TiposEvento/TipoEventoPadrao` (scoped): `Nomes` (Corrida, Treino, CrossFit, Moto passeio, Casamento, Academia, Outro) e `CriarPadroesAsync(assinanteId, ct)`, que só inclui no contexto (`InsertRangeTransactionAsync`, não salva). Chamado por `AssinanteInicializacao` (na transação do `AssinanteController.Criar`) e pelo `Seed` (que salva).
- Models em `Models/Cadastros/` (`TipoEventoModel`, `TipoEventoListItem`, `OpcaoModel`); validator em `Validators/TipoEvento/`.

## MembroController (plano 02, etapa 3; só Assinante; `api/Membro/*`)
Mesmo desenho do `TipoEventoController`. Campos `MEM_NOME`, `MEM_INSTAGRAM` (gravado sem "@"), `MEM_EMAIL`, `MEM_TELEFONE` (só dígitos), `MEM_FUNCAO` (enum `FuncaoMembro` como número: 1 Fotografo, 2 Editor, 3 Assistente), `MEM_OBSERVACOES`; `MEM_ATIVO` só na saída. `Listar` ganha `funcao` (int; fora do enum = 400 "Filtro de função inválido"); a busca procura em nome, instagram (sem "@") e e-mail, e no telefone quando o termo sem pontuação tem só dígitos; ordena por `MEM_NOME`, `Id`. Instagram preenchido e repetido no assinante (sem diferenciar maiúsculas, contando inativos) = 400 "Já existe um membro com este Instagram.". **E-mail e telefone preenchidos não podem repetir** em outro membro do mesmo assinante (ativos e inativos; no Atualizar exclui o próprio Id; sem índice único, checagem no controller, `GarantirContatoUnicoAsync`): 400 `Já existe o membro "<Nome>" com este e-mail.` / `... com este telefone.`, com ` (inativo)` após o nome quando for o caso (e-mail é checado antes do telefone). Normalização: trim, e-mail em minúsculas, tira "@" do início e espaços do instagram, telefone só dígitos, opcional vazio vira `null`.

## OrganizadorController (plano 02, etapa 4; só Assinante; `api/Organizador/*`)
Mesmo desenho do `TipoEventoController`/`MembroController`. Campos `ORG_NOME` (obrigatório, até 200, **não único**: o nome pode repetir), `ORG_CONTATO` (150), `ORG_EMAIL` (opcional, até 200, minúsculas), `ORG_TELEFONE` (só dígitos), `ORG_INSTAGRAM` (sem "@", até 100), `ORG_NOTAS` (2000); `ORG_ATIVO` só na saída. **E-mail e telefone preenchidos não podem repetir** em outro organizador do mesmo assinante (ativos e inativos; no Atualizar exclui o próprio Id; checagem no controller, sem índice único): 400 `Já existe o organizador "<Nome>" com este e-mail.` / `... com este telefone.`, com ` (inativo)` após o nome quando for o caso. `Listar` (`page`, `pageSize`, `busca`, `ativo`): a busca procura em nome, contato, e-mail e instagram, e no telefone quando o termo sem pontuação tem só dígitos; ordena por `ORG_NOME`, `Id`. `OrganizadorListItem` não traz `ORG_NOTAS`. O histórico do organizador fica para o plano de Eventos.

## EventoController (plano 03, etapas 2 a 4; só Assinante; `api/Evento/*`)
Mesmo desenho do `OrganizadorController`. Datas trafegam como "yyyy-MM-dd" (`DateOnly`) e horas como "HH:mm:ss" (`TimeOnly?`; nulo = "a confirmar"). `StatusEvento` (1 Pendente, 2 Confirmado, 3 Realizado, 4 Cancelado) e `TipoArquivoEvento` (1 Flyer, 2 ImagemRota, 3 Gpx) são números. Nunca saem `*_ASSINANTE_ID`, `EVA_CAMINHO`, `CreatedAt`, `UpdatedAt`.
- **Cadastro**: `GET Listar` (`page`, `pageSize` máx. 100, `busca` em nome/cidade, `dataDe`/`dataAte` como texto "yyyy-MM-dd", `status`, `tipoEventoId`, `organizadorId`, `ordem` asc|desc na data; inválido = 400; dentro do dia: hora com "a confirmar" por último, nome, Id; cada item traz `TipoEventoNome`, `OrganizadorNome` e `Equipe` [{Id do membro, MEM_NOME, MEM_INSTAGRAM}]), `GET Obter?id=` (`EventoModel` com `TipoEventoNome`, `OrganizadorNome`, `Arquivos`), `POST Criar`, `PUT Atualizar`, `DELETE Excluir?id=`. Obrigatórios: nome, tipo, data (anos 2000 a 2100), status e **cidade**; hora e organizador opcionais. Links só `http`/`https`; textos longos até 4000 (colunas `longtext`). Tipo e organizador precisam ser do assinante (400 "... não encontrado.") e ativos, exceto se já forem o valor gravado (400 "... inativo."). `Excluir` apaga escala, pendências, link, registros de arquivo e evento numa transação e, depois do commit, os arquivos físicos (falha = `LogWarning`).
- **Agenda** (plano 04, etapa 1; sem migration): `GET Agenda?dataDe=&dataAte=&status=&tipoEventoId=&cidade=&membroId=` devolve `EventoListItem[]` (sem paginação, com `Equipe`, inclui cancelados salvo filtro de status). `dataDe` e `dataAte` obrigatórias ("yyyy-MM-dd", inclusivas); **no máximo 62 dias contando os dois extremos**. 400 em texto: "Informe o período", "Data inicial inválida", "Data final inválida", "A data inicial não pode ser maior que a data final", "O período não pode passar de 62 dias", "Filtro de status inválido". `tipoEventoId`/`membroId` vazios ou `Guid.Empty` são ignorados (id de outro assinante = lista vazia); `cidade` aparada, igualdade (collation do MySQL ignora maiúsculas), vazia é ignorada; `membroId` filtra pela escala (`EVENTOXMEMBRO`, mesmo assinante). Ordem igual à do `Listar` (data, hora com "a confirmar" por último, nome, Id). `GET Cidades` devolve `string[]` das `EVE_CIDADE` distintas do assinante (todos os status e datas), aparadas, sem vazias, em ordem alfabética pt-BR. O `Distinct` roda no MySQL: com a collation padrão (`*_ai_ci`), grafias que só diferem em acento ou maiúsculas ("São Paulo" x "Sao Paulo") viram uma entrada só, e o filtro `cidade` da `Agenda` também as junta, então combo e filtro ficam coerentes (a confirmar no banco real). `Listar` e `Agenda` compartilham os métodos privados `ParseData`, `ValidarStatus`, `ProjecaoListItem` e `CarregarEquipeAsync`.
- **Escala** (`Services/Eventos/EscalaConsultas`, ponto único do conflito): `GET Membros?id=`, `GET OpcoesEscala?id=`, `POST AdicionarMembro` (`{EVM_EVENTO_ID, EVM_MEMBRO_ID, EVM_POSICAO}`), `PUT AtualizarMembro?id=` (só a posição), `DELETE RemoverMembro?id=` (o `id` dessas duas é o Id da linha da escala), `GET Dia?data=yyyy-MM-dd` (`Eventos` com `Equipe` e `EmConflito`, `Livres`, `Conflitos`). **Conflito** = mesmo membro em 2 ou mais eventos na mesma data, ignorando a hora; Cancelados não contam, Realizados contam; calculado na leitura (`OutrosEventos`), nunca gravado e **nunca bloqueia**. Só membro ativo pode ser escalado (400 "Membro inativo."); quem for inativado depois continua com `MEM_ATIVO = false`; membro repetido = 400 "Este membro já está escalado neste evento." (inclusive pelo índice único). Escala em evento de qualquer status.
- **Arquivos** (`IArquivoStorage` no CrossCutting; hoje só `ArquivoStorageDisco`, singleton): `POST EnviarArquivo?id=<evento>&tipo=1|2|3` (multipart, campo `Arquivo`, `RequestSizeLimit` de 11 MB), `GET BaixarArquivo?id=<arquivo>` (`File()` com o nome original, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`), `DELETE ExcluirArquivo?id=<arquivo>`. Regras em `Services/Eventos/ArquivoEventoRegras`: imagens JPG/PNG/WEBP até 5 MB (extensão **e** assinatura dos bytes; o content-type gravado é o da assinatura), GPX até 10 MB (extensão `.gpx` e XML com `<gpx`). Um arquivo de cada tipo por evento: enviar outro substitui. Ordem: grava o arquivo no disco, depois o banco; se o banco falhar apaga o novo; o antigo só é apagado depois do commit. A chave é `<assinante>/<evento>/<guid>.<ext>` gerada pelo servidor (o nome do usuário nunca entra; `EVA_NOME_ORIGINAL` é só exibição, higienizado) e o `ArquivoStorageDisco` recusa chave com `..`, `\`, caminho absoluto ou que saia da pasta base. Arquivo de outro assinante ou ausente do disco = 404 "Arquivo não encontrado".
- **Armazenamento**: `Arquivos:Pasta` no appsettings (vazio = `<ContentRoot>/App_Data/arquivos`; relativo é resolvido a partir do ContentRoot; recusa pasta dentro do `wwwroot`). A pasta fica fora do `wwwroot` (nunca servida como estático); o `csproj` exclui `App_Data\**` do build/publish e o `.gitignore` ignora `AgendaFotografo.WebApi/App_Data/`. Em produção apontar para uma pasta persistente fora da pasta de publicação e incluí-la no backup: no container (Dokploy) é `/app/dados/arquivos` (variável `Arquivos__Pasta` no compose), no volume `agenda-arquivos` do `docker-compose.yml` (ver `docs/deploy.md`).
- Models em `Models/Eventos/` (`EventoModel`, `EventoListItem`, `EventoEquipeItem`, `EventoArquivoItem`, `EventoResumo`, `EventoMembroModel`/`EventoMembroPosicaoModel`, `EventoMembroItem`/`OpcaoEscalaItem`, `DiaResponse` e itens); validators em `Validators/Evento/`.

## Link público (plano 05; tabela `EVENTOLINKS`, `EVL_`)
Cada evento pode ter um link `/e/<token>` protegido por código de 4 dígitos. Código, token e acesso **nunca** vão para o log.
- **Coordenador** (`EventoController`, perfil Assinante, evento carregado por `Id` **e** assinante, senão 404; respostas com `Cache-Control: no-store`): `GET Link?id=` (`EventoLinkItem`: `Configurado`, `EVL_ATIVO`, `EVL_MOSTRAR_EQUIPE`, `EVL_TOKEN`, `Codigo`; sem link = 200 com `Configurado = false`), `PUT AtualizarLink?id=` (body `EventoLinkModel` com `EVL_ATIVO` e `EVL_MOSTRAR_EQUIPE`; sem link cria, com link muda só as duas chaves), `POST RegerarCodigoLink?id=` (novo código + carimbo, token igual) e `POST RegerarLink?id=` (novo token, código e carimbo). Sem link, as regerações dão 400 "Crie o link público primeiro.". Criação e regerações geram `LogInformation` com `EventoId` e `AssinanteId`. `Excluir` do evento apaga o link na mesma transação.
- **Anônimo** (`LinkPublicoController`, `api/LinkPublico/*`): classe com `[Authorize(Roles = Assinante)]` (trava padrão) e `[EnableRateLimiting("LinkPublico")]`; **cada action com `[AllowAnonymous]`**; nenhuma usa `AssinanteEscopo` nem devolve 401 (derrubaria o coordenador logado que abre o link). `OnActionExecuting` põe `no-store` e `X-Robots-Tag: noindex` em toda resposta. O token (query ou body) é aparado, minúsculo e validado (32 hexadecimais) antes de ir ao banco; token inválido = mesmo 404 de "indisponível".
  - `POST Acessar` (`{Token, Codigo}` + `X-Aparelho`): formato do código (400 "Digite o código de 4 números.", não conta) -> link indisponível (404 "Link indisponível. Peça o link atualizado ao coordenador.", não conta; vale para token inexistente, link desativado, evento excluído e `ASS_ATIVO = false`) -> reserva da tentativa (429 "Muitas tentativas erradas. Tente de novo em N minutos." sem comparar) -> comparação em tempo constante. Certo = 200 `LinkPublicoAcessoResponse {Acesso, ExpiraEm}`; errado = 400 "Código incorreto. Restam N tentativas." ("Resta 1 tentativa."), e a 5ª falha do aparelho (ou 10ª do IP) já responde 429.
  - `GET Evento?token=` (`X-Acesso-Link`) -> `EventoPublicoModel` (lista branca montada campo a campo; `Equipe` nula quando `EVL_MOSTRAR_EQUIPE` está desligado). `GET Arquivo?token=&tipo=1|2|3` (flyer, imagem de rota, GPX) -> `File()` com nosniff; outro tipo ou arquivo ausente = 404 "Arquivo não encontrado". Sem acesso válido (ausente, inválido, vencido, de outro link ou de carimbo antigo) = 403 "Digite o código do evento.". Nunca saem Ids, assinante, organizador, tipo, status (só `Cancelado`), `EVE_LINK_INSCRICAO`, notas internas, contato dos membros, `EVA_CAMINHO`.
- **Segredos** (`Services/LinkPublico/LinkPublicoSegredos`, singleton): token e carimbo = 16 bytes de `RandomNumberGenerator` em hexadecimal minúsculo; código = 4 dígitos sorteados, sem 4 iguais, sem sequência simples e diferente do anterior; comparação com `CryptographicOperations.FixedTimeEquals`. O acesso é um JWT (emissor/audiência `AgendaFotografo.LinkPublico`, claims `lid` e `car`, 7 dias, `ClockSkew` zero) com chave derivada por HKDF do `Jwt:Key` (diferente da do login); o SPA o envia em `X-Acesso-Link`, nunca em `Authorization`. Novo carimbo invalida todos os acessos; desativar bloqueia e reativar devolve o acesso dentro dos 7 dias.
- **Links curtos do Maps** (`Services/Locais/LinkMapsExpansor`, `AddHttpClient` sem auto-redirect, timeout 5 s): no `GET Evento` do link público, `EVE_ROTA_LINK_MAPS`, `EVE_LARGADA_LINK` e `EVE_CHEGADA_LINK` em `maps.app.goo.gl`/`goo.gl/maps` viram o link completo (o SPA só incorpora o link completo). Segue no máximo 5 redirecionamentos e só para hosts do Google (sem SSRF; tela `consent.` usa o `?continue=`), cache de 1 dia em `IMemoryCache`; qualquer falha devolve o link original. Nada é gravado no banco.
- **Tentativas** (`LinkPublicoTentativas`, singleton sobre `IMemoryCache`, sempre por link): aparelho (`X-Aparelho` = 8 a 64 caracteres `[A-Za-z0-9-]`; inválido/ausente usa o IP) 5 erros em 15 min bloqueiam 15 min; IP 10 erros. A tentativa é reservada **antes** de comparar (sob lock); acerto zera o aparelho e devolve a reserva do IP; bloqueado não compara nem o código certo; cada bloqueio gera `LogWarning` com o Id do link e o IP. **Contadores em memória: a API deve rodar com uma só instância** (sem bloqueio global por link, para não travar a equipe).
- **Program.cs**: `UseForwardedHeaders` primeiro (`X-Forwarded-For`/`X-Forwarded-Proto`, `ForwardLimit = 1`; `ForwardedHeaders:KnownProxies` e `ForwardedHeaders:KnownIPNetworks` do appsettings/variáveis, nunca limpas para confiar em todos; valor inválido derruba a subida com mensagem clara). `AddRateLimiter` com a política `LinkPublico` (60 req/min por IP, janela fixa, 429 "Muitas requisições. Aguarde um minuto e tente de novo."); `UseRateLimiter` depois de `UseRouting` e `UseCors`. Faixa de rede de produção: ver `docs/deploy.md` (provisória).
- Models: `Models/Eventos/EventoLinkItem`/`EventoLinkModel`; `Models/LinkPublico/` (`LinkPublicoAcessoModel`, `LinkPublicoAcessoResponse`, `EventoPublicoModel`, `EventoPublicoEquipeItem`).

## Pendências do evento (plano 06; tabela `EVENTOPENDENCIAS`, `EVP_`; actions do `EventoController`, só Assinante)
Tabela filha do evento, sem controller próprio. Enums como número (`Domain/Enums`): `StatusPendencia` (1 AFazer, 2 EmAndamento, 3 Concluida, 4 Ignorada), `PrioridadePendencia` (1 Alta, 2 Media, 3 Baixa), `CategoriaPendencia` (1 Contrato, 2 EscalaEquipe, 3 RotaInformacoes, 4 PlataformaFotos, 5 Equipamento, 6 EntregaFotos, 7 Organizador, 8 Outros). Nunca saem `EVP_ASSINANTE_ID`, `CreatedAt`, `UpdatedAt`. Pendências **nunca** entram no link público.
- **Actions** (assinante só de `AssinanteEscopo`; 403 antes do `catch`; escritas em transação): `GET Pendencias?id=<evento>` (ordem da ficha: abertas, concluídas e ignoradas, nessa ordem; em cada grupo prazo com "sem prazo" por último, prioridade, título, Id; evento de outro assinante = 404 "Evento não encontrado"), `POST AdicionarPendencia` (`EventoPendenciaModel` sem `Id`; evento de qualquer status; devolve `EventoPendenciaItem`), `PUT AtualizarPendencia` (body com `Id`; sem Id = 400 "Id é obrigatório"; outro assinante = 404 "Pendência não encontrada"; **ignora** `EVP_EVENTO_ID` do body), `PUT AtualizarStatusPendencia?id=` (body `{EVP_STATUS}`, só o status), `DELETE ExcluirPendencia?id=` (exclusão real, `ApiResponse`), `GET ListarPendencias` (abaixo).
- **Cadastro**: título aparado, obrigatório, até 200; categoria/prioridade/status dentro do enum; prazo `DateOnly?` entre 2000 e 2100; observações até 2000 (vazio vira null); `EVP_MEMBRO_ID` `Guid.Empty` vira null. Responsável: do assinante (400 "Membro não encontrado.") e ativo (400 "Membro inativo."), a menos que já seja o gravado (`GarantirResponsavelAsync`).
- **`ListarPendencias?page=1&pageSize=25&status=&prioridade=&membroId=&prazo=`**: só eventos **não cancelados** do assinante; `pageSize` máx. 100. `status`: vazio/`abertas` (padrão: A fazer e Em andamento), `todas` (inclui as ignoradas), `1`, `2`, `3`, `4` (só ignoradas; outro = 400 "Filtro de status inválido"); `prioridade` 1 a 3 (400 "Filtro de prioridade inválido"); `membroId` vazio/`Guid.Empty` ignorado, de outro assinante = lista vazia; `prazo`: vazio/`todos`, `vencidas`, `vencendo`, `vencidasOuVencendo` (sem diferenciar maiúsculas; outro = 400 "Filtro de prazo inválido"), valendo só para abertas. GUID/número malformado = 400 "Filtro inválido". Ordem: prazo (sem prazo por último), prioridade, data do evento, título, Id.
- **`Services/Eventos/PendenciaConsultas`** (scoped; **ponto de reuso dos avisos (`AvisoConsultas`) e do e-mail de lembretes do módulo 13**): único lugar das regras de prazo. `DiasAVencer = 3`; **Aberta** = A fazer ou Em andamento (predicado único `PendenciaConsultas.Abertas` / `EhAberta`; Concluída e Ignorada são estados finais e não entram em lista "abertas", prazo nem contadores); **Vencida** = aberta com prazo antes de hoje; **Vencendo** = aberta com prazo de hoje até hoje + 3; evento Cancelado nunca vence; sem prazo nunca vence. Calculadas na leitura (`CalcularPrazo`), nunca gravadas. "Hoje" é parâmetro: o controller passa `DateOnly.FromDateTime(DateTime.Now)` (o `Dockerfile` fixa `TZ=America/Sao_Paulo`). Projeção única para `EventoPendenciaItem` (traz `MEM_NOME`/`MEM_ATIVO`, `EVE_NOME`/`EVE_DATA`/`EVE_STATUS`, `Vencida`, `Vencendo`, `EVP_MODELO_ID`).
- **`GET ContarPendencias?prioridade=&membroId=`** (plano 09; `no-store`; mesmas validações do `ListarPendencias`: prioridade fora de 1 a 3 = 400 "Filtro de prioridade inválido", malformado = 400 "Filtro inválido"; `membroId` vazio/`Guid.Empty` ignorado, de outro assinante = tudo zero) -> `PendenciasContagemResponse { Abertas, Vencidas, Vencendo, Concluidas, Ignoradas }`. `ContarAsync` usa os mesmos métodos privados (`BaseFiltrada`, `AplicarPrazo`) da `ListarAsync` e do `ResumoPrazoAsync`. **Invariante**: cada contador = `TotalCount` do `ListarPendencias` equivalente (Abertas = `status=abertas`; Vencidas/Vencendo = `status=abertas&prazo=...`; Concluidas = `status=3`; Ignoradas = `status=4`), com os mesmos `prioridade`/`membroId`.
- Apoio aos avisos (plano 08): `ResumoPrazoAsync(assinanteId, hoje)` -> `ResumoPrazo { Vencidas, TitulosVencidas, Vencendo, TitulosVencendo }` (quantidades pelas mesmas regras de `CalcularPrazo`, eventos não cancelados, e os 3 primeiros títulos por prazo, prioridade, título) e `AbertasPorEventoAsync(assinanteId, eventoIds)` -> `Dictionary<Guid, int>` com as abertas por evento **sem** a categoria Entrega das fotos.
- Progresso por evento (plano 10): `ContarPorEventoAsync(assinanteId, eventoIds)` -> `Dictionary<Guid, (int Abertas, int Total)>`, duas consultas agrupadas (sem N+1). Total usa o predicado `PendenciaConsultas.NaoIgnoradas` (status diferente de Ignorada) e Abertas usa `Abertas`; **todas as categorias contam** (inclusive Entrega das fotos, diferente de `AbertasPorEventoAsync`, que segue sem ela e inalterado). Só eventos não cancelados: Cancelado ou sem pendência = 0 e 0. `EventoController.PreencherPendenciasAsync` preenche `PendenciasAbertas`/`PendenciasTotal` (int) em `EventoListItem` (`Listar` e `Agenda`) e em `DiaEventoItem` (`Dia`). Feitas = Total - Abertas.
- Models em `Models/Eventos/` (`EventoPendenciaModel`, `EventoPendenciaStatusModel`, `EventoPendenciaItem`); validators em `Validators/Evento/EventoPendenciaValidator.cs`. Sem concorrência/lock (cadastro simples).

## Checklist padrão de pendências (plano 07; tabela `PENDENCIAMODELOS`, `PEM_`)
Todo evento novo nasce com um checklist de pendências a partir dos modelos do assinante; o coordenador ignora as que não valem.
- **`PendenciaModeloController`** (`api/PendenciaModelo/*`, só Assinante; molde `TipoEventoController`): `GET Listar?page&pageSize&busca&situacao&tipoEventoId` (`situacao`: `ativos` padrão | `inativos` | `todos`, outro = 400 "Filtro de situação inválido"; ordem: todos os tipos primeiro, tipo, `PEM_DIAS_ANTES` decrescente, título, Id; devolve `PendenciaModeloListItem` com `TPE_NOME`/`TPE_ATIVO`, nulos = "Todos os tipos"; **o checklist nasce vazio: nenhum modelo é criado automaticamente, nem para assinante novo**), `GET Obter?id=`, `POST Criar`, `PUT Atualizar` (`PendenciaModeloModel`; `PEM_ATIVO` do body é ignorado; tipo de outro assinante = 400 "Tipo de evento não encontrado."; `Id` vazio = 400 "Id é obrigatório"; inexistente/outro assinante = 404 "Modelo não encontrado"), `POST Inativar?id=` / `POST Ativar?id=` (idempotentes, 200 `ApiResponse`). **Sem Excluir.** Editar um modelo **não altera** pendências já criadas. Validator `PendenciaModeloValidator`: título obrigatório até 200, categoria e prioridade no enum, `PEM_DIAS_ANTES` de -90 a 365 (positivo = antes, negativo = depois, nulo = sem prazo).
- **`Services/Pendencias/PendenciaChecklistPadrao`** (scoped; só inclui no contexto, **nunca salva**): **não há semente**: a lista nasce vazia e o assinante cadastra os próprios modelos (CRUD em `PendenciaModelo`; nunca se apaga, só inativa); `AplicarAsync(assinanteId, evento, hoje, ignorarModelosJaAplicados)` cria uma pendência (A fazer, sem responsável, com `EVP_MODELO_ID`) por modelo ativo do tipo do evento ou de "todos", com prazo `EVE_DATA - DiasAntes` (**nulo se anterior a hoje** ou fora de 2000-2100) e devolve a quantidade. Chamado por `Evento/Criar` e `Evento/AplicarChecklist`. **Recorrência (melhoria futura)**: cada ocorrência gerada deve chamar `AplicarAsync` com a data da ocorrência; ela não copia as pendências da série anterior.
- **`Evento/Criar`** gera o checklist na mesma transação (falha desfaz o evento); editar o evento ou trocar o tipo **não** gera pendências; os eventos existentes não recebem backfill.
- **`POST Evento/AplicarChecklist?id=<evento>`**: evento de outro assinante = 404 "Evento não encontrado"; acrescenta só os modelos ainda não representados no evento (ignorada conta como representada; idempotente; vale também em evento Cancelado); devolve `EventoAplicarChecklistResponse { Adicionadas, Itens: EventoPendenciaItem[] }` na ordem da ficha. O índice único `(EVP_EVENTO_ID, EVP_MODELO_ID)` barra duplicata por clique duplo.
- **`Ignorada = 4`**: `AtualizarStatusPendencia` e os filtros aceitam o 4; restaurar = voltar para A fazer. O `EVP_MODELO_ID` só sai em `EventoPendenciaItem` (etiqueta "Padrão") e nunca entra pelo `EventoPendenciaModel`. Link público continua sem pendências.

## Avisos (plano 08; sem tabela e sem migration; `AvisoController`, só Assinante)
Tudo é calculado na hora, sem "lido/não lido". **Fonte única** para o sino do cabeçalho, a tela Início e o **e-mail diário de lembretes (módulo 13, deve chamar `AvisoConsultas.ListarAsync`, nunca reimplementar as regras)**.
- **`GET api/Aviso/Listar`** (`[Authorize(Roles = Assinante)]`; Admin = 403): assinante só de `AssinanteEscopo`, 403 de vínculo antes do `catch`, "hoje" = `DateOnly.FromDateTime(DateTime.Now)`, `Cache-Control: no-store`, `ErrorHelper.Seguro`. Resposta `AvisosResponse { Total, Criticos, Itens }` (`Models/Avisos/`).
- **`AvisoItem`**: `Chave` (estável, `trackBy`), `Tipo` (`TipoAviso`), `Gravidade` (`GravidadeAviso`), `Titulo`, `Descricao`, `Detalhes` (`string[]`), `Quantidade` (nos agrupados e nos conflitos = nº de eventos; senão 0), `EventoId`, `Data` ("yyyy-MM-dd"), `MembroId`. A API não conhece URLs do SPA. Enums como número: `TipoAviso` 1 PendenciasVencidas, 2 PendenciasVencendo, 3 EventoProximo, 4 ConflitoEscala, 5 EventosPassadosSemBaixa; `GravidadeAviso` 1 Critico, 2 Atencao.
- **`Services/Avisos/AvisoConsultas`** (scoped): constantes únicas `DiasAFrente = 7`, `DiasEventoChegando = 3`, `DiasPassado = 30`, `LimiteItens = 30`. Usa `PendenciaConsultas` (predicado `Abertas`, `ResumoPrazoAsync`, `AbertasPorEventoAsync`) e `EscalaConsultas.ConflitosNoPeriodoAsync` (conflito por data, hora ignorada, Cancelado não conta).
- **Regras**: (1) `PendenciasVencidas`: abertas com prazo antes de hoje, eventos não cancelados; 1 aviso agrupado, sempre Crítico, `Chave` `pendencias-vencidas`. (2) `PendenciasVencendo`: abertas com prazo de hoje até hoje + 3; agrupado, Atenção, `pendencias-vencendo`. (3) `EventoProximo`: evento não cancelado de hoje até hoje + 7 com algum problema, 1 por evento, `Chave` `evento-proximo:<id>`; problemas em `Detalhes` e a `Descricao` os junta ("Sem equipe, sem rota"): Pendente = "Ainda não confirmado"; Confirmado = "Sem equipe" (nenhuma linha em `EVENTOXMEMBRO`), "Sem rota" (sem link Maps, sem Strava, sem arquivo ImagemRota e sem Gpx), "Sem hora", "Sem local de largada" (local **e** link de largada vazios); qualquer status, só se a data é de hoje até hoje + 3: "N pendências abertas" (abertas, sem Entrega das fotos). Sem problema = sem aviso. (4) `ConflitoEscala`: mesmo membro em 2+ eventos não cancelados na mesma data, de hoje até hoje + 7; 1 por membro e dia, `Chave` `conflito:<membro>:<data>`, `MembroId` e `Data` preenchidos. (5) `EventosPassadosSemBaixa`: Pendente ou Confirmado com data nos últimos 30 dias, antes de hoje; agrupado, Atenção, `eventos-passados-sem-baixa`, `Data` = o evento **mais antigo** (o SPA abre a Agenda nesse mês).
- **Gravidade**: Vencidas e qualquer `EventoProximo`/`ConflitoEscala` de hoje ou amanhã = Crítico; o resto = Atenção. Ordem: gravidade, data (aviso sem data primeiro), título, chave. No máximo 30 itens; `Total` e `Criticos` são os reais (contam todos os avisos, não só os devolvidos).
- **Consultas**: eventos da janela em uma consulta (só os campos necessários), equipe, arquivos de rota e pendências de todos os ids de uma vez (sem N+1). Nunca lê `EVE_NOTAS_INTERNAS`, informações, observações nem dados do organizador; os textos só usam nome do evento, data, nome do membro e títulos de pendência.
- Dia da semana abreviado em tabela própria ("sáb 14/11"), sem depender da cultura do servidor.

## Chat / Assistente com IA (plano 11; sem tabela e sem migration; `ChatController`, só Assinante)
Ajuda o coordenador a lançar eventos a partir de uma mensagem colada (ex.: WhatsApp). **A IA nunca grava**: ela só devolve um rascunho; quem grava, ao confirmar, é o SPA, com `Evento/Criar` e `Evento/AdicionarMembro` (o `Criar` já gera o checklist; **não** chamar `AplicarChecklist`). O histórico fica só no SPA e é reenviado a cada mensagem (a API não guarda nada).
- **Pacotes** (CrossCutting): `Microsoft.Extensions.AI` 10.11.0, `Microsoft.Extensions.AI.OpenAI` 10.11.0 e `Azure.AI.OpenAI` 2.1.0 (a 2.1.0 é a última **estável**; as mais novas são beta).
- **Configuração** (`IA` no appsettings; em produção `IA__*` no `agenda-api`): `Provedor` (`OpenAI` padrão | `AzureOpenAI`; outro valor desliga o chat com `LogWarning`), `ApiKey`, `Modelo` (nome do modelo; no Azure, o nome do deployment), `Endpoint` (opcional na OpenAI, onde vira a URL base de um provedor compatível; obrigatório e URL absoluta no Azure) e `LimiteDiario` (padrão 100). `IASettings.Ligado` = provedor conhecido, `ApiKey` e `Modelo` preenchidos (+ `Endpoint` válido no Azure). Configuração incompleta **desliga o chat sem quebrar a subida**: o `IChatClient` nem é registrado e `ChatAvisoInicial` (IHostedService) loga `LogWarning` (sem valores). A chave nunca vai ao SPA, a docs nem a logs. Passo a passo: `docs/ia.md`. Os dados das mensagens são processados fora do Brasil.
- **Cliente** (`CrossCutting/Services/IA/IAExtensions.AddIAChat`, chamado em `Setup.RegisterCustomServices`): OpenAI direta = `new OpenAIClient(new ApiKeyCredential(key), options).GetChatClient(modelo).AsIChatClient()`; AzureOpenAI = `AzureOpenAIClient` (Azure.AI.OpenAI 2.1.0) com o endpoint. Ambos com `UseFunctionInvocation` de **no máximo 5 iterações** por requisição e timeout de **60 s** (`NetworkTimeout` do cliente + `CancelAfter` no controller). **O chat depende do `proxy_read_timeout 120s` do `location /api/` do `nginx.conf` do SPA** (conferido; o timeout de 60 s fica abaixo). Mudar um exige revisar o outro.
- **`GET api/Chat/Status`** -> `ChatStatusResponse { Ligado, LimiteDiario, UsadasHoje }` (`no-store`).
- **`POST api/Chat/Enviar`** (`[RequestSizeLimit]` 3 MB): corpo `ChatEnviarModel { Mensagens: [{ Papel: 1|2, Texto, Rascunho?, Imagem? }] }` -> `ChatEnviarResponse { Texto (até 2.000), Rascunho, Eventos }` (`Rascunho` único ou nulo; `Eventos` 0 a 10 `EventoResumo`; `no-store`). O `Texto` devolvido é cortado em 2.000. Ordem: vínculo (403) -> chat desligado (400 "O assistente não está disponível.") -> validação -> limite diário -> modelo. Validação (400 em texto): 1 a 20 mensagens, cada texto não vazio, até 2.000 caracteres **só no papel Usuario** (resposta longa do assistente no histórico é cortada em 2.000 ao montar o histórico, não dá 400), total até 12.000 (depois do corte), `Papel` dentro de `PapelChat` (1 Usuario, 2 Assistente; **não existe papel "sistema" vindo do cliente**), última mensagem do usuário. Falha, timeout ou filtro de conteúdo do provedor = 400 "Não foi possível falar com o assistente agora. Tente de novo." (`LogWarning` só com `AssinanteId` e o tipo do erro). Limite estourado = **429** "Você atingiu o limite de N mensagens de hoje. Tente de novo amanhã.". Resto = `ErrorHelper.Seguro`.
- **Histórico**: o `Rascunho` de uma mensagem do assistente vira um resumo textual curto (com os ids, só texto) anexado à mensagem, para refinamentos ("muda para 8h"); os ids são sempre revalidados no `ProporEvento`.
- **Imagem do flyer (plano 12)**: `ChatMensagemItem.Imagem { MediaType, Base64 }` só na **última** mensagem e só no papel Usuario (senão 400 "Mensagem inválida."). Validada **antes** da reserva do limite diário: Base64 inválido = "Imagem inválida."; mais de 2 MB decodificados = "A imagem deve ter no máximo 2 MB."; bytes que não são JPG, PNG nem WEBP = "A imagem deve ser JPG, PNG ou WEBP." O `MediaType` informado é ignorado: vale o tipo detectado por `ArquivoEventoRegras.DetectarImagem(bytes)` (assinatura dos bytes; usado também pelo `Evento/EnviarArquivo`, que mantém as mesmas mensagens). Texto vazio é aceito quando há imagem (o servidor usa "Leia este flyer e monte o rascunho do evento."); sem texto e sem imagem continua "Escreva uma mensagem.". A última mensagem vai ao modelo como `TextContent` + `DataContent`. **A imagem nunca é logada, gravada em disco nem guardada em cache**: fica só em memória na requisição; o log de uso ganha só `ComImagem=true|false`. Mensagem com imagem conta **1** no limite diário. O modelo precisa aceitar imagem (ver `docs/ia.md`). O `RequestSizeLimit` de 3 MB cabe no `client_max_body_size 12m` do `nginx.conf` do SPA (conferido, não mudou). A imagem não é anexada ao evento.
- **`Eventos` da resposta**: `ChatFerramentas.Eventos` (zerado em `Montar`) junta, sem repetir Id e no máximo 10, os eventos devolvidos por `BuscarEventos` e `ConsultarDia` na requisição (`EventoResumo`); os ids ficam só no servidor e nunca vão ao modelo. O front não os reenvia no histórico.
- **`ChatRascunho.Semelhantes`**: `ProporEvento` procura eventos **não cancelados** do assinante entre a data -1 e +1 dia com nome parecido (nomes normalizados em minúsculas, sem acento nem pontuação; parecidos quando um contém o outro ou quando ao menos 60% das palavras de 3 ou mais letras do menor estão no outro). Até 3 em `Semelhantes` + aviso em `Avisos` (`Já existe "X" em 20/11 (Confirmado).`); nunca bloqueia. `ProporEvento` ganhou `linkInscricao` (`EVE_LINK_INSCRICAO`, normalizado e validado pelo `EventoValidator`: só http/https; o `ResumirRascunho` o inclui). Se a segunda chamada de `ProporEvento` da resposta for recusada, o controller acrescenta ao `Texto` a frase fixa "Os outros eventos da mensagem ficam para depois: confirme este e me peça o próximo."
- **`Services/Chat/ChatFerramentas`** (scoped): `Montar(assinanteId)` fixa o assinante (vindo só de `AssinanteEscopo`) e devolve as funções; **nenhuma ferramenta recebe assinante como parâmetro** e todas filtram por ele. Só leitura: `ListarTiposEvento`, `BuscarOrganizadores(busca)` (até 20), `BuscarMembros(nomes)` (até 5 por nome, por nome ou Instagram, só ativos), `ListarCidades` (mesma consulta do `Evento/Cidades`, `CidadesConsulta`), `ConsultarDia(data)` (resumo de `EscalaConsultas.ObterDiaAsync`; alimenta o coletor `Eventos`) e `BuscarEventos(texto?, dataDe?, dataAte?, status?, membroId?)` (plano 12, ver abaixo). Devolvem o mínimo: sem e-mail, telefone, observações, notas internas nem informações de eventos. `ProporEvento(nome, tipoEventoId, data yyyy-MM-dd, hora HH:mm|nulo, cidade, local?, organizadorId?, informacoes?, membros[{membroId, posicao?}], membrosNaoEncontrados?)` aplica `EventoNormalizacao` + `EventoValidator`, confere tipo/organizador/membros do assinante e **ativos** (id de outro assinante ou inexistente é recusado), fixa `EVE_STATUS = Pendente`, preenche `TipoEventoNome`/`OrganizadorNome`, calcula `OutrosEventos` com `EscalaConsultas.OutrosEventosAsync` (conflito só avisa) e guarda o rascunho (nomes em `membrosNaoEncontrados` viram `Avisos` "Não encontrei: ..."). **No máximo um rascunho por resposta**: a segunda chamada válida recebe "Já há um rascunho nesta resposta; proponha o próximo depois que o usuário confirmar.". Nenhuma ferramenta chama Insert/Update/Delete/SaveChanges.
- **`BuscarEventos`** (plano 12; só leitura, assinante capturado, sem parâmetro de assinante): `texto` = até 5 palavras de 3 ou mais letras, cada uma precisa aparecer em nome, cidade, local ou nome do tipo (a collation ignora acento e maiúsculas); `status` 1 a 4; `membroId` vem de `BuscarMembros` (de outro assinante = lista vazia, a escala é filtrada pelo assinante). Período: sem datas e sem texto = hoje a hoje + 30; sem datas e com texto = hoje - 365 a hoje + 365; só `dataDe` = até `dataDe` + 30; só `dataAte` = desde hoje; o máximo de 366 dias vale para o período pedido (o padrão com texto é a exceção); data inválida, invertida ou período grande demais = mensagem curta ao modelo. Ordem: futuros primeiro (crescente) e depois passados (decrescente), no máximo **10** itens mais `Total`. **Resultado em texto compacto (uma linha por evento, não JSON), para economizar tokens**; `ConsultarDia` também devolve texto compacto. Cada linha traz data, dia da semana, hora, nome, tipo, cidade/local, status, organizador (**só o nome**) e pendências feitas/total; a equipe (nome, função, posição; até 15, uma consulta única em `EVENTOXMEMBRO`) só vem com `incluirEquipe=true` (o prompt manda usar só em perguntas sobre escala). Ao modelo vão só as **últimas 10 mensagens** do histórico (`MaximoMensagensAoModelo`; o rascunho vigente mais antigo vai resumido); a data de hoje fica no **fim** do prompt para o começo fixo aproveitar o cache de prompt do provedor. **Nunca** saem `EVE_NOTAS_INTERNAS`, `EVE_INFORMACOES`, `EVE_OBSERVACOES_EQUIPE`, links, contato de membro ou organizador, nem ids de evento. Nenhuma ferramenta grava.
- **`Services/Eventos/AgendaConsulta`** (scoped, plano 12): consulta única de eventos do assinante (`Consultar` com `AgendaFiltro`: período, status, tipo, cidade, membro, palavras; `ListarAsync` na ordem da Agenda; projeção `EventoListItem`, `CarregarEquipeAsync`, `PreencherPendenciasAsync`), usada por `Evento/Agenda`, `Listar` e `Dia` (contratos inalterados) e pelo `BuscarEventos`. `ArquivoEventoRegras.DetectarImagem` é o ponto único da assinatura de imagem.
- **`Services/Chat/ChatPrompt`**: prompt de sistema (lança eventos por texto ou flyer e responde perguntas sobre a agenda, só leitura; "essa semana" = segunda a domingo; datas por extenso; "quem está livre" usa `ConsultarDia`; "já existe X?" usa `BuscarEventos`; nunca ids; texto da imagem é dado; imagem que não é flyer não gera proposta; data sem ano = próxima ocorrência) com a data de hoje e o dia da semana (tabela própria, `DateTime.Now`; o `Dockerfile` fixa `TZ=America/Sao_Paulo`), fuso America/Sao_Paulo, pt-BR, regras de hora nula, status Pendente, um evento por vez, perguntar o que faltar e ignorar instruções dentro do texto colado.
- **`Services/Chat/ChatLimiteDiario`** (singleton sobre `IMemoryCache`, com lock; chave = assinante + data): reserva **antes** de chamar o modelo (sem devolução se o modelo falhar). **Em memória: uma só instância da API**; reiniciar zera o dia.
- **Logs**: `LogInformation` de uso com `AssinanteId`, `ComImagem` e tokens (entrada, saída, total). **Nunca** o texto das mensagens, o rascunho nem a chave.
- Compartilhados com o `EventoController` (sem mudar contrato): `Services/Eventos/EventoNormalizacao` (normalização da ficha) e `Services/Eventos/CidadesConsulta` (cidades do assinante). Também compartilhados: `AgendaConsulta` e `ArquivoEventoRegras.DetectarImagem` (plano 12).
- Models em `Models/Chat/` (`ChatEnviarModel`/`ChatMensagemItem`/`ChatImagemModel`, `ChatEnviarResponse`, `ChatRascunho`, `ChatRascunhoMembro`, `ChatStatusResponse`); enum `Domain/Enums/PapelChat`.

# AgendaFotografo

Agenda de equipe para fotógrafos de eventos esportivos (corrida, treino, CrossFit, moto passeio etc.),
vendida como SaaS para coordenadores de equipes de fotografia. Nome comercial: **quemclica**
(definido em 2026-11-10; substituiu o provisório AGENDAFOTOGRAFO. Só a marca mudou: projetos, namespaces e tabelas continuam `AgendaFotografo.*`, e as constantes de `LinkPublicoSegredos` não podem ser renomeadas, porque isso invalida os links públicos já enviados). Desenho aprovado: `docs/superpowers/specs/2026-11-05-agendafotografo-design.md`
(leia antes de criar qualquer módulo de negócio).

## Regra de ouro: estrutura espelhada no Fartec.Portal
O back-end segue **exatamente** a estrutura, os nomes e as convenções do `Fartec.Portal` (referência obrigatória, somente leitura:
`/Users/eduardokopp/Profissional/FartecSistemas/Fartec.Portal`). Onde o Portal diverge do padrão do plugin `fartec`, **vale o Portal**.
Antes de criar qualquer controller, model, validator, map ou migration, abra o equivalente no Portal (`ClienteController`,
`MerecimentoController`, `AuthController`, `Setup.cs`, `Seed.cs`) e copie o desenho. Regras do Portal que são de negócio dele
(apontamento, texto em maiúsculas automático, e-mail marketing, importadores) **não** fazem parte deste projeto.

## Decisões do projeto
- Sistema: AgendaFotografo
- Estrutura: padrão Fartec (Domain / Infra.Data / CrossCutting / WebApi / WebSPA), espelhando o Fartec.Portal, com **uma única WebApi** (`AgendaFotografo.WebApi`) e **um único SPA** (`AgendaFotografo.WebSPA`)
- API: **uma API só, um controller base (`AgendaFotografoController`, rota `api/[controller]/[action]`)**; o perfil é controlado por `[Authorize(Roles = ...)]` em cada controller (como no Portal). Não existe prefixo `api/Admin`.
- SPA: **um SPA só, perfis separados por rota** (`/admin/...`, `/assinante/...`; decisão do colaborador). Não criar SPAs por perfil.
- Modelo de acesso: Assinante + Administração (multi-tenant). Perfis **`Admin`, `Assinante` (coordenador) e `Fotografo`** (plano 20; plano 21: conta própria **grátis, sem teste de 15 dias e sem agenda pessoal**, que só vê os eventos em que um coordenador o escalou pelo documento (CPF ou CNPJ); o Admin não cria fotógrafo). **Plano 23: o coordenador escalado por outro coordenador também vê esses eventos, só leitura, pelo mesmo documento**. O Assinante (coordenador) é o tenant e faz login no dia a dia; ele se cadastra sozinho (módulo 14: e-mail e senha ou Google, com 15 dias de teste grátis; no cadastro manual, **com o e-mail ligado, o e-mail é confirmado por um código de 6 números** antes de entrar, módulo 18) ou é criado pelo Admin (criado pelo seed), que também ativa e bloqueia assinantes. A equipe de fotógrafos só faz login se tiver conta de Fotografo (cadastro próprio, grátis; o vínculo com o coordenador é só pelo CPF ou CNPJ gravado na Equipe). Não há `UsuarioAssinante`, permissões granulares nem planos.
- Cor principal: #F97316 (marca, só sem texto); primário de ação #C2410C (texto branco); apoio #7C2D12 (marrom). Paleta no `tailwind.config.js` do SPA (plano 16)
- Logo (escolhida em 2026-11-10, opção "agenda que clica"): calendário laranja com argolas e faixa marrons, a lente no meio e o "click!" (três traços laranja) saindo do canto + texto "quem." / "clica" (o ponto é só da logo; nos textos o nome é "quemclica"), em `src/assets/images/logo/` do SPA; o mesmo ícone no favicon e no PWA. Cópias em `docs/marca/` (logo, logo branca e o ícone em 512 px)
- Banco: **MySQL** (Pomelo.EntityFrameworkCore.MySql), servidor zeus.fartecsistemas.com.br, banco EduardoDbNaoApagar (credenciais no appsettings.json)
- Financeiro: carteira do coordenador (plano 22): receitas, despesas e gastos fixos do próprio assinante; continua sem valor, pago, repasse ou cliente comercial **dentro dos eventos** (nada de vínculo evento x dinheiro); recurso a ser pago no futuro, hoje liberado para todo coordenador. Desenho: `docs/superpowers/specs/2026-11-23-financeiro-carteira-design.md`
- Uso em celular e computador (telas responsivas); o link público é mobile-first

## Regras do banco (IMPORTANTE)
- Nada é executado direto no banco: sem SQL manual, sem `CREATE DATABASE/TABLE`, sem `dotnet ef database update`. A estrutura vem só das migrations do EF Core, aplicadas pela API ao iniciar (`MigrateDatabaseAsync`). Iniciar a API acessa o banco (inclusive `ServerVersion.AutoDetect`): o colaborador decide quando.
- Tabelas em MAIÚSCULAS, inclusive as do Identity (`ASPNETUSERS`, `ASPNETROLES` etc.), como no Portal. Detalhes e convenção de nomes no `CLAUDE.md` do Infra.Data.
- Credenciais ficam só no `appsettings.json`; nunca repetir senha em CLAUDE.md, docs ou relatórios. Exceção decidida pelo colaborador: a senha padrão do admin do seed fica no código (`Seed.SenhaPadraoAdmin`) e vai para o git.

## Estrutura da solução (`AgendaFotografo.sln`, .NET 10)
| Projeto | Papel |
|---|---|
| `AgendaFotografo.Domain` | Entidades, interfaces (`IBaseRepository`, `IUnitOfWork`), `RoleNames`. Não referencia ninguém. |
| `AgendaFotografo.Infra.Data` | `EfDbContext`, maps, interceptor de auditoria, repositórios, migrations (MySQL/Pomelo). |
| `AgendaFotografo.CrossCutting` | Regras FluentValidation reutilizáveis (CPF/CNPJ, e-mail, telefone, senha, endereço) e serviço de e-mail (`IEmailService`/`EmailService`, MailKit). |
| `AgendaFotografo.WebApi` | **API única** (login, área do assinante e área administrativa). Porta http 5289 / https 7118. Ver o `CLAUDE.md` dela. |
| `AgendaFotografo.WebSPA` | **SPA único** Angular 18 + Fuse (porta 4200): Admin, assinante e link público, separados por rota; o `Role` do login define a área. Ver o `CLAUDE.md` dele. |

Namespaces: `AgendaFotografo.<Projeto>` (a API usa `AgendaFotografo.WebApi`).

```bash

dotnet run --project AgendaFotografo.WebApi    # aplica migrations e seed ao iniciar (acessa o banco!)
# SPA (Node 22): em AgendaFotografo.WebSPA, npm install; npm start (http://localhost:4200); npm run build
# nova migration: NÃO acessa o banco (a EfDbContextFactory do Infra.Data fixa o MySQL 8.0.36 com connection string fictícia)
dotnet ef migrations add <NomeEmPascalCase> --project AgendaFotografo.Infra.Data --startup-project AgendaFotografo.WebApi
```

## Deploy (Dokploy, VM Hostinger)
Docker Compose na raiz (`docker-compose.yml`): `agenda-web` (Nginx com o build do Angular, proxy de `/api/` para a API; único serviço com domínio),
`agenda-api` (`Dockerfile` da raiz, `ASPNETCORE_ENVIRONMENT=Production`) e `agenda-mysql` (MySQL 8.0, banco `agenda_fotografo`; porta 3307 publicada só em `127.0.0.1` da VM, para acesso por túnel SSH, ver `docs/deploy.md`).
A landing page (plano 13, HTML estático em `AgendaFotografo.WebSPA/src/landing/`) é entregue pelo mesmo Nginx em `/`; o domínio é `quemclica.com.br` e o `www.quemclica.com.br` redireciona (301) para ele no próprio Nginx.
Há **um só** `appsettings.json`, sempre no zeus (o `fartec:testador` bloqueia se qualquer connection string dos appsettings não for o zeus): **não criar
`appsettings.Production.json`**. Produção sobrescreve por variáveis de ambiente do `agenda-api` no compose (`ConnectionStrings__DefaultConection` para o banco do
container, `Arquivos__Pasta=/app/dados/arquivos`, num volume). A connection string de produção vem do Environment do Dokploy (`AGENDA_DB_CONNECTION`, obrigatória: sem ela o deploy falha); o `docker-compose.yml` só traz as credenciais do serviço `agenda-mysql` (exceção decidida pelo colaborador). Também vêm do Environment: `AGENDA_GOOGLE_CLIENT_ID`, `AGENDA_TESTE_DIAS_GRATIS` e as do e-mail da conta (`AGENDA_MAIL_REMETENTE`, `AGENDA_MAIL_USUARIO`, `AGENDA_MAIL_SENHA`, `AGENDA_MAIL_HOST`, `AGENDA_MAIL_PORTA` e `AGENDA_URL_SISTEMA`, todas opcionais; vazias = e-mail desligado) (tabela completa em `docs/deploy.md`).
Passo a passo e pontos de atenção em `docs/deploy.md`. Endpoint ou arquivo novo que mude porta, tamanho de upload ou pasta persistente: revisar `nginx.conf`, compose e Dockerfiles.

## Regras transversais
- **Multi-tenancy**: todo dado de negócio pertence a um assinante. O id do tenant vem **sempre do banco** via `AssinanteEscopo.ObterAssinanteIdAsync` (lê `Usuario.AssinanteId`), nunca de claim, body ou query. Em Update/Delete, carregar por `Id` **e** assinante.
- **Assinante inativo** (`ASS_ATIVO = false`): bloqueia o login (400) e derruba a sessão em até ~30 s (401 por `OnTokenValidated` + `SessaoUsuarioCache`); quem altera `ASS_ATIVO` deve chamar `SessaoUsuarioCache.Invalidar` para cada usuário do assinante.
- **JSON**: `PropertyNamingPolicy = null` (nomes C# exatos no JSON), `ReferenceHandler.IgnoreCycles`. Renomear propriedade quebra o front.
- **Enums**: valores numéricos fazem parte do contrato com o front; manter sincronia back↔front.
- **Senha**: única regra é o mínimo de 8 caracteres (validator + Identity). `Usuario.ExigirTrocaSenha` força a troca no SPA.
- **Endpoints anônimos de cadastro** (módulo 14): `api/Auth/Cadastrar`, `LoginGoogle` e `CadastrarGoogle` têm `[AllowAnonymous]` e a política de rate limit `Cadastro` (10 requisições por minuto por IP, 429 em texto; contadores em memória); `ConfiguracaoLogin` é anônima e não acessa o banco (traz `EmailLigado`). Respostas com token levam `Cache-Control: no-store`.
- **Endpoints anônimos de e-mail da conta** (módulo 18): `api/Auth/ConfirmarEmail`, `ReenviarCodigo`, `CorrigirEmail`, `EsqueciSenha` e `RedefinirSenha`, todos `[AllowAnonymous]`, com a política `Cadastro` e `no-store`; com o e-mail desligado respondem 400 "O envio de e-mails não está disponível no momento.". As três primeiras conferem e-mail e senha pelo mesmo `ConferirSenhaAsync` do `Login` (com lockout). Código de 6 números, 15 min, uso único, 5 erros invalidam, 60 s entre envios; guardado só como hash HMAC em `ASPNETUSERTOKENS` (sem migration). `EsqueciSenha` responde sempre o mesmo 200. Nunca logar código, e-mail, senha, assunto ou corpo. Detalhes no `CLAUDE.md` da WebApi.
- **Financeiro** (plano 22): `LANCAMENTOS` (`LAN_`) e `GASTOSFIXOS` (`GAF_`) são só do dono: `LancamentoController`, `GastoFixoController` e `Dashboard/Financeiro` têm `[Authorize(Roles = Assinante)]` (Admin e Fotógrafo = 403), tenant só por `AssinanteEscopo`, Update/Delete por Id **e** assinante. **Nenhum outro fluxo lê essas tabelas** (Admin, Assistente/IA, avisos, Início, link público, e-mails). Nunca logar título, valor nem observações (só `AssinanteId` e quantidades). Gasto fixo gera Despesa ao abrir o Financeiro (preguiçoso, idempotente, sem serviço em segundo plano). Detalhes no `CLAUDE.md` da WebApi.
- **Vínculo por documento** (planos 20 e 23): o casamento é pelo documento da conta (`ASS_CPF_CNPJ`: CPF de 11 ou CNPJ de 14 dígitos válidos, sempre CPF com CPF e CNPJ com CNPJ) com `Membro.MEM_CPF` (coluna `varchar(14)`, nome mantido) de OUTROS coordenadores ativos, e a regra existe só em `EscalaFotografoConsultas`. Vale para a conta Fotografo (`EscalaController`) e para o Assinante escalado por outro coordenador (`EscalaCoordenadorController`, plano 23, `[Authorize(Roles = Assinante)]`, rota `api/EscalaCoordenador/*`, somente leitura); o `EventoController` não foi afrouxado (próprios + escala de fora só se juntam no SPA). É vivo (calculado a cada leitura; removido da escala, evento excluído, documento trocado/apagado ou coordenador bloqueado = some; cancelado continua marcado). O coordenador nunca descobre se o documento tem conta (o `MembroController` não lê `ASSINANTES` nem `ASPNETUSERS`). `MEM_CPF` só trafega no `MembroModel` (`Obter`/`Criar`/`Atualizar`). Quem é escalado vê só uma lista branca (campo a campo, mais `TemFlyer`; o flyer vale para os dois perfis), com o mesmo 404 "Evento não encontrado." para qualquer evento sem vínculo. Riscos aceitos (plano 23): o documento da conta não é provado, um único documento por conta, coordenador criado pelo Admin sem documento não recebe eventos de outras equipes. Nunca logar documento. Detalhes no `CLAUDE.md` da WebApi.
- **Endpoints anônimos** (link público `/e/{token}`, `api/LinkPublico/*`, módulo 5 pronto): `[AllowAnonymous]` na action, código de 4 dígitos, 5 erros bloqueiam 15 min por aparelho, acesso liberado por 7 dias. `ForwardedHeaders` (IP real atrás de proxy) já está no `Program.cs`, configurado por `ForwardedHeaders:KnownProxies` e `ForwardedHeaders:KnownIPNetworks` (no compose: `ForwardedHeaders__KnownIPNetworks__0`, variável `AGENDA_REDE_CONFIAVEL`; confirmar a faixa real do Dokploy, ver `docs/deploy.md`). Contadores de tentativas ficam em memória: **uma só instância da API**. Nunca expor notas internas, pendências ou dados do organizador.
- **Configuração** (`appsettings.json` da WebApi, convenção da equipe): `ConnectionStrings:DefaultConection` (grafia mantida; traz a senha), `Jwt` (`Key`, `ExpiraEmHoras`), `MailSettings` (`Mail`, `DisplayName`, `Password`, `Host`, `Port`), `MailSettings` também tem `Usuario` (login do SMTP; vazio = `Mail`), `UrlSistema` (base dos links e imagens dos e-mails; vazio ou inválido = `https://quemclica.com.br`) e `GravarEmPasta` (padrão `true`, só lido no Development). **Modo do e-mail decidido na subida**: Smtp (Host, Mail e Password preenchidos), Pasta (só Development, configuração incompleta e `GravarEmPasta` diferente de `false`: grava `.html` em `App_Data/emails`) ou Desligado (todo o resto, inclusive Production sem configuração: o cadastro manual entra direto, sem boas-vindas e sem "Esqueci minha senha"). Provedor escolhido: ZeptoMail (`smtp.zeptomail.com`, 587, remetente `no-reply@quemclica.com.br`; os e-mails não recebem respostas). `Seed:AdminPassword` (opcional; vazio usa `Seed.SenhaPadraoAdmin`), `Cors:Origins`, `Teste:DiasGratis` (padrão 15; dia do cadastro conta como o 1º; inválido ou menor que 1 vale 15) e `Google:ClientId` (não é segredo; vazio = sem botão do Google; a validação do ID token é sempre na API, com `Google.Apis.Auth`; em produção `Teste__DiasGratis` e `Google__ClientId`). `IA` (`Provedor` OpenAI|AzureOpenAI, `ApiKey`, `Modelo`, `Endpoint` opcional, `LimiteDiario` padrão 100): assistente com IA (`ChatController`); `ApiKey` ou `Modelo` vazio desliga o chat, a chave nunca vai ao SPA, a docs nem a logs, e os dados são processados fora do Brasil; em produção `IA__*` no `agenda-api` (ver `docs/ia.md`). `Geoapify:ApiKey`: chave do autocomplete de locais (`LocalController`/`LocalBusca`; a API repassa a busca à Geoapify e a chave nunca vai ao SPA; vazia desliga as sugestões). Sobrescritas opcionais: `Db:Password`, `Jwt:Key`, `Seed:AdminPassword`, `Cors:Origins` por User Secrets (Development) ou variáveis de ambiente (`Db__Password` etc.).
- **Arquivos** (flyer, imagem de rota, GPX): **disco**, atrás de `IArquivoStorage` (CrossCutting; o Blob pode entrar depois sem mexer nos controllers), numa pasta fora do `wwwroot` (`Arquivos:Pasta`; vazio = `<ContentRoot>/App_Data/arquivos`, ignorada pelo git e fora do publish). Imagens JPG/PNG/WEBP até 5 MB, GPX até 10 MB; detalhes no `CLAUDE.md` da WebApi.

## Perfis
- `Admin`: back-office; criado pelo seed (`admin@agendafotografo.com.br`, senha padrão em `Seed.SenhaPadraoAdmin`). Não tem assinante.
- `Assinante`: coordenador; dono do tenant (`Usuario.AssinanteId`). Tem origem (`OrigemAssinante`: 1 Admin, 2 Autocadastro) e `ASS_TESTE_ATE` (último dia do teste grátis; nulo = sem prazo; prazo vencido ainda não bloqueia nada).
- `Fotografo` (plano 20): conta própria (`TipoAssinante.Fotografo`, `ASS_TIPO` = 2; também é um `Assinante`/tenant, só que sem tipos de evento padrão) vê, pelo documento (CPF ou CNPJ), só os eventos dos coordenadores em que está escalado (`EscalaController`, só leitura). **Plano 21 (23/11/2026): é grátis e não tem teste** (`ASS_TESTE_ATE` sempre nulo; o aviso de teste é só do coordenador) **e a agenda pessoal do plano 20 está desligada e guardada**: o `EventoPessoalController` responde 403 "A agenda pessoal não está disponível." por uma constante única (`AgendaPessoalLigada = false`), e a entidade `EventoPessoal`, a tabela `EVENTOSPESSOAIS` e os dados ficam, sem migration. Cadastra-se sozinho (CPF ou CNPJ obrigatório, plano 23); o Admin vê, bloqueia, reativa e redefine o acesso, mas não cria. Sem `UsuarioAssinante`, permissões granulares e planos. Os controllers do coordenador continuam `[Authorize(Roles = Assinante)]` (fotógrafo = 403).
- `api/Auth` (`Login`, `AlterarSenha`, `SolicitarCodigoDefinirSenha` e `DefinirSenha` (plano 19, `[Authorize]`), e as anônimas `ConfiguracaoLogin`, `Cadastrar`, `LoginGoogle`, `CadastrarGoogle`; `TesteGratis` é do coordenador: para o Fotografo responde nulo, plano 21) é comum; o `Role` devolvido no login define para onde o SPA direciona.
